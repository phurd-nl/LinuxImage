LUKS + TPM Login-Time /home Encryption

Setup guide for the LinuxEncryption scripts. Encrypts /home with LUKS2, seals the unlock key to the TPM (clevis tpm2), and auto-unlocks it at login via PAM.

These scripts are destructive and they touch disk partitions and LUKS keyslots. Read this whole page once before running anything. A single wrong value in scripts/config.sh can reformat the wrong drive. Have a working, off-machine backup before step 1, and store the recovery passphrase somewhere physical. When in doubt, stop and inspect — every script guards before acting and aborts loudly.

What you get

  • /home lives on an encrypted LUKS2 volume; it is encrypted at rest whenever you are logged out.
  • At login, a PAM hook has the TPM release the key, opens the volume, mounts it at /home, and shreds the key from memory. At logout it unmounts and re-locks.
  • Three ways in: keyslot 0 = your login password (kept in sync automatically), keyslot 1 = an offline recovery passphrase, keyslot 2 = the TPM-sealed random key.
  • Swap lives inside the encrypted volume, so it is also encrypted at rest. Suspend-to-disk is disabled.
  • After hardening, the key is sealed to PCR 7 only (Secure Boot state) so routine firmware/BIOS updates don't lock you out, with a self-heal path for the rare Secure-Boot-key change.

Configure & back up

Edit scripts/config.sh for the target machine. These four values are the only things that identify your box — everything else (install paths, PCR policy) is a design constant.

DISK=/dev/nvme0n1     # whole disk that gets the new partition
PARTNUM=4             # partition number to create / encrypt
USERNAME=phurd        # login user whose /home is encrypted
MAPPER=home_crypt     # /dev/mapper name for the opened volume

LUKS_DEV is derived automatically (nvme0n1 + 4 → /dev/nvme0n1p4; sda + 2 → /dev/sda2). Confirm your disk and free space against reality, and sanity-check the derivation:

lsblk -o NAME,SIZE,FSTYPE,TYPE,MOUNTPOINT   # find your disk & free space
bash scripts/test-config.sh                 # verify the LUKS_DEV derivation rule
Then back up. Copy the user's home directory to an external drive or network location. The original stays in place until step 6, but the off-machine backup is your net for the partition-table edit.
1

Enable Secure Boot

Reboot into UEFI firmware → enroll / restore the default Secure Boot keys (if the platform is in Setup Mode) → enable Secure Boot → save & exit. Back in Linux, confirm:

mokutil --sb-state        # must say: SecureBoot enabled

Why first: PCR 7 measures Secure Boot state. Enabling it before sealing makes the seal stable and avoids an immediate re-seal.

2

Create the encrypted partition

sudo bash scripts/01-create-partition.sh

Shows the current layout, then creates the partition from the largest free block. It refuses if the partition already exists and never touches existing partitions. Type CREATE to proceed.

3

Encrypt, migrate, seal, wire up PAM

sudo bash scripts/02-setup-encryption.sh

This is the main event. It will:

  1. Pre-flight: refuses unless Secure Boot is on, TPM is present, and the target partition is empty and unmounted.
  2. Install packages, then LUKS2-format the partition. At the first prompt, enter your login password — it becomes keyslot 0.
  3. Copy /home into the encrypted volume (original left intact) and create an encrypted swapfile inside it.
  4. Add a recovery passphrase (keyslot 1). Choose a strong one and write it down / store it offline right now — this is your only way in if the TPM is ever cleared.
  5. Generate a random key (keyslot 2), seal it to the TPM, verify it unseals, and shred the plaintext key.
  6. Install the login open/close hooks, the password-sync hook, and the kernel-update reseal hook; wire them into PAM.
At this point the original plaintext /home still exists on the unencrypted root partition. That is intentional — you do not wipe it until a reboot proves the encrypted volume works.
4

Reboot and verify

Reboot (a fresh boot is the real test, not just re-login), log in, then:

sudo bash scripts/after-reboot.sh         # is /home the encrypted volume this boot?
sudo bash scripts/verify-encryption.sh    # full non-destructive check (slots, JWE, hooks, PAM, swap)

You want findmnt /home to show /dev/mapper/<MAPPER> and verify-encryption.sh to end with FAIL=0. Then log out and back in and re-run verify-encryption.sh to confirm the steady-state login mount.

Do not proceed to the wipe (step 6) until this passes cleanly across a real reboot and a logout/login cycle.
5

Harden against firmware updates

Out of the box the key is sealed to PCRs 0,2,4,7 — PCR 0 changes on every firmware update, which would lock out auto-unlock. This re-seals to PCR 7 only and installs a self-heal path. Run it while logged in with /home unlocked:

sudo bash scripts/08-harden-tpm-pcr7-selfheal.sh

Then confirm the self-heal credential path works end-to-end (it does not touch keyslots or the sealed key):

sudo bash scripts/test-selfheal.sh arm
sudo -k ; sudo -v                          # one authentication (same PAM path as GDM)
sudo bash scripts/test-selfheal.sh check

Reboot once more and re-run after-reboot.sh + verify-encryption.sh. After this, run firmware/BIOS updates normally — no manual reseal needed.

tradeoff Sealing to PCR 7 only means the seal no longer detects firmware tampering (it still detects booting a different or unsigned OS). With Secure Boot enforcing signatures this is the standard, accepted choice. Your recovery passphrase remains the floor.
6

Wipe the old plaintext /home

Irreversible. Only after steps 4–5 passed across a reboot, and your backup is intact.
sudo bash scripts/04-purge-shadowed-plaintext-home.sh

The old plaintext copy of /home still sits, shadowed, on the unencrypted root partition underneath the encrypted mount. This bind-mounts the real root filesystem to reach it and deletes it, with hard guards: it refuses unless the live /home is the encrypted mapper and the shadowed copy is on a different block device. Type WIPE to confirm. It optionally scrubs the freed blocks afterward.

Done. Your home data now exists only on the encrypted volume. Verify one last time with verify-encryption.sh.

Recovery & maintenance

Keep this section — and your recovery passphrase — reachable from a different machine or on paper.

Everyday facts

  • Change your login password normally. The password-sync hook keeps keyslot 0 in step. If it ever drifts, the recovery passphrase (keyslot 1) still works.
  • Firmware/BIOS updates are fine after step 5. A rare Secure-Boot-key change may trigger self-heal on the next login (transparent).
  • Kernel updates are handled by the installed clevis-reseal hook.

If /home did not auto-unlock at login

The login hook is session optional, so on failure it silently drops to a plaintext /home rather than locking you out. Diagnose, then reseal:

journalctl -t home-crypt -b               # what the hook logged this boot
# unlock manually with a passphrase you know, then reseal to current PCRs:
sudo clevis-reheal                        # prompts for login OR recovery passphrase

Before removing any keyslot (07 or a manual luksKillSlot): prove a known passphrase still opens the volume. Keep at minimum keyslot 0 (login), your recovery passphrase, and the TPM keyslot. Losing the wrong slot is irreversible.

Last-resort: unlock from a live USB

If the PAM hook is broken and you can't log in, boot a live USB and open the volume with your recovery passphrase:

sudo cryptsetup open /dev/<your-partition> recovered   # enter recovery passphrase
sudo mount /dev/mapper/recovered /mnt                  # your data is under /mnt
